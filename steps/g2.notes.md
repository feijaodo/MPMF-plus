# g2 - history_mode on by default; one resolver; README "Switches"

## What changed
- `paths.DEFAULTS["history_mode"] = True`; `config.example.json` carries `"history_mode": true`.
- One resolver, `paths.history_mode()` (env `MPMF_HISTORY_MODE` > config file > default True; the same boolean
  rule for file and env: 1/true/yes/on = on, anything else off). `provider._history_mode()` and `history.enabled()`
  both call it. Before: `provider._history_mode()` read the JSON directly (missing key -> off, env ignored) and
  `history.enabled()` honoured env first - they could disagree.
- Nightly auto-revert (`eval/nightly.py::_revert_history`) now writes an explicit `"history_mode": false`
  (key removal would turn it back ON with the default on) and keeps the PAUSED.md row. `eval/autoapply.py`'s revert
  was checked: it restores the previous state of the key it applied, never `history_mode`; no change needed.
- Tests: `tests/test_g2_history_default.py` (fresh install, env 0, explicit false wins, revert -> every reader off).
  `tests/test_autorevert_pairing.py` asserted "key removed" after a revert; it now asserts `history_mode is False`
  (the new contract, same simulated drop). Disclosed: this existing test was edited because the behaviour it pinned
  was changed on purpose.

## Open finding (not changed here; g6 decides defaults)
`rerank_skip_after_ms: 0` (the live setting, called "reranker off on prefetch" in the 0.3.0 changelog) is read as
`float(value or 4500)` in `provider._rerank_skip_after_ms`, so a file value of 0 resolves to 4500 (checked: 0 -> 4500.0).
Same pattern for `prefetch_budget_ms` (0 -> 6500). Whether the live reranker is really off is therefore not
established by the setting alone.
